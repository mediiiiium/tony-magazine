## 1. 全体コンセプト・売り方の基本方針

### 1-1. 前提となる問題意識

受託がしんどくなる原因はスキル不足ではなく**商品設計**にある。

| 切り売り型（避ける） | 商品型（目指す） |
|---|---|
| 「1件ヒアリングして作ります」 | 「完成済みのものを設定して渡します」 |
| 見積もり・要件定義から毎回スタート | 価格・納品物・範囲が固定 |
| 納品後の質問対応が無限に伸びる | マニュアルが質問を吸収する |
| 売上 ＝ 稼働時間 × 単価（上限あり） | 売上 ＝ 販売本数 × 単価（上限なし） |

### 1-2. 基本方針：「商品 ＋ マニュアル」構成

納品物を必ず次の3点セットにする。これが崩れると即座に時間の切り売りに戻る。

1. **本体**（GASスクリプト / 静的化済みサイト / テンプレート）
2. **導入マニュアル**（スクリーンショット付き。初回設定を顧客が自分でできる粒度）
3. **運用マニュアル＋FAQ**（よくある質問を先回りで潰す。ここが利益率を決める）

> ポイント：マニュアルは「おまけ」ではなく**商品の主要部分**。
> マニュアルの質 ＝ サポート工数の削減量 ＝ 実質時給。

### 1-3. 価格帯の設計（3階層）

| 階層 | 内容 | 価格イメージ | 狙い |
|---|---|---|---|
| **入口**：ノウハウ/テンプレ販売 | 手順書・スクリプト本体のみ。設定は自分でやってもらう | 1,000〜5,000円 | 実績数・レビュー数を稼ぐ。工数ほぼゼロ |
| **中核**：導入代行パッケージ | 本体＋初期設定＋マニュアル。作業は定型化済み | 15,000〜50,000円 | 現金と実績を作る。ただし**時間を消費するので件数に上限をかける**（7章） |
| **上位**：カスタマイズ/保守 | 個別要件の追加開発、月額サポート | 個別見積 / 月額 | 単発を継続収入に変える |

入口商品でレビューを集め、中核商品に導線を引くのが基本の流れ。

> **重要**：代行（中核）は利益の柱ではなく、**ストック商品を作るための資金と素材の調達手段**として位置づける。
> 代行を最終ゴールに置くと、売れるほど時間が無くなる構造から抜けられない。詳細は7章。

### 1-4. 売り文句の作り方

技術名ではなく**顧客の損失**を主語にする。

- ✗「GASで業務を自動化します」
- ○「毎日30分の転記作業を、月1,000円未満のコストでゼロにします」
- ✗「Cloudflareに移行します」
- ○「サーバー代が毎月かかっているサイトを、表示速度を上げたうえで**永久0円**にします」

## 2. 軸①：GAS（Google Apps Script）ツール・パッケージ

### 2-1. GASを選ぶ理由

- **サーバー不要**：Googleアカウントさえあれば動く。顧客側のインフラ費用が0円
- **納品が軽い**：スクリプトをコピー ＋ トリガー設定だけで完了する形に持ち込める
- **Googleサービスと直結**：スプレッドシート / フォーム / Gmail / カレンダー / ドライブ
- **横展開しやすい**：1本作れば、業種を変えて文言だけ差し替えて再販できる

### 2-2. 商品案A：AI連携系（ChatGPT / Gemini API）

| 商品 | 中身 | 想定顧客 |
|---|---|---|
| スプレッドシートAI関数 | `=GPT("要約して", A2)` のようなカスタム関数。列一括処理対応 | 一般事務・マーケ担当 |
| レビュー/アンケート自動分析 | フォーム回答を自動で感情分類・要約・タグ付けしてシートに追記 | 店舗・EC・人事 |
| 記事/商品説明文の量産ツール | キーワード列を入れると本文案が生成される | ブロガー・EC事業者 |
| メール下書き自動生成 | 受信メールをトリガーに返信案をGmail下書きへ保存 | 個人事業主・営業 |
| 議事録要約Bot | ドライブに置いた文字起こしを要約してSlack/LINEへ通知 | 小規模チーム |

**納品設計の要点**

- APIキーは**顧客自身に取得してもらう**（取得手順を図解マニュアル化）
  → 自分のキーを使わせると従量課金を被り、赤字リスクが青天井になる
- スクリプトプロパティにキーを保存する方式にし、コード内に直書きしない
- モデル名・プロンプト文はシートの設定タブから変更できるようにする
  → 「文体を変えたい」という要望が仕様変更ではなく**顧客の操作**で片づく
- 実行回数・トークン消費の目安を明記（想定コストを事前に共有）

### 2-3. 商品案B：定常業務の自動化系（AI不要・安定して売れる）

| 商品 | 中身 |
|---|---|
| フォーム→自動返信＋台帳化 | 申込フォーム受付 → 自動返信メール → シート台帳 → 担当者へ通知 |
| LINE公式連携 | フォーム回答やシート更新をLINEへ通知。予約リマインドの自動送信 |
| 定期レポート配信 | 毎朝/毎週、シートを集計してPDF or メールで自動送付 |
| 請求書・見積書の自動生成 | シート1行 → Googleドキュメント差し込み → PDF化 → ドライブ保存 → 送信 |
| 在庫・予約管理シート | 重複予約の排除、在庫閾値でのアラート通知 |
| カレンダー連携 | シートの予定を一括でカレンダー登録／変更を双方向同期 |
| ドライブ整理 | 命名規則にそったフォルダ自動生成・ファイル自動振り分け |

AI連携より地味だが、**壊れにくく・説明が簡単で・値引き交渉されにくい**。
売上の土台はこちら側に置くのが安全。

### 2-4. 納品フロー（定型化する）

```
1. 事前ヒアリングシート（固定質問10問）に回答してもらう ← 通話しない
2. こちらでスクリプト設定＋シート雛形を用意
3. 顧客のGoogleアカウントで実行できる形にして共有
4. マニュアル（PDF or Notion）を渡す
5. 動作確認 → 納品。以降の質問はFAQへ誘導
```

**ヒアリングを固定質問化するのが最大の時短ポイント。**
「打ち合わせしましょう」を1回やった時点で利益率は半減すると考える。

### 2-5. 制約として先に伝えておくこと

- GASの実行時間上限（1回あたり最大6分程度）。大量データはバッチ分割が必要
- 1日あたりのメール送信数・トリガー実行時間にGoogle側の上限がある
- 共有ドライブ/組織アカウントの権限設定によっては動かない場合がある
- Googleの仕様変更で将来的に改修が必要になる可能性がある（後述の免責へ）

## 3. 軸②：WordPress → Cloudflare（静的化・無料化）

### 3-1. 提供価値（売り文句の核）

| 顧客の現状 | 移行後 |
|---|---|
| レンタルサーバー代が毎月1,000〜3,000円 | **サーバー代 永久0円**（Cloudflare Pages 無料枠） |
| 表示が重い／PageSpeedが低い | 静的配信＋CDNで**爆速化**（SEO・離脱率に直結） |
| WordPressの脆弱性・改ざんが怖い | 静的HTMLなので**攻撃対象がほぼ消える** |
| プラグイン更新・PHP更新の管理が面倒 | 更新作業から解放される |
| アクセス集中で落ちる | CDN配信で耐障害性が上がる |

年間コスト換算で「1.2万〜3.6万円/年の削減 ＋ 高速化 ＋ セキュリティ向上」。
移行費用が数万円でも**1〜2年で回収できる**という説明が刺さる。

### 3-2. 基本の移行手順

```
1. 現行WordPressの完全バックアップ（DB＋ファイル）
2. 静的化：WP2Static / Simply Static などで静的HTML書き出し
   （またはローカル環境で生成 → 出力物だけを使う）
3. 出力物をGitリポジトリへ格納
4. Cloudflare Pages に接続してデプロイ
5. 独自ドメインをCloudflareのネームサーバーへ変更（DNS切替）
6. リダイレクト設定・フォーム代替・404チェック
7. 表示・リンク・画像・SSLの最終検品
```

### 3-3. 動的機能の置き換え表

静的化で**必ず**論点になる部分。事前に置き換え先を提示できると強い。

| 元の機能 | 置き換え先 |
|---|---|
| お問い合わせフォーム | Googleフォーム / Formspree / Cloudflare Workers ＋ GAS（← 軸①と接続できる） |
| コメント欄 | 外部サービス（Disqus等）or 廃止 |
| サイト内検索 | 静的検索（Pagefind等）or Google カスタム検索 |
| 会員限定ページ | Cloudflare Access / 別途SaaS。**静的化では原則対象外** |
| ECカート | Stripe決済リンク / 外部カート埋め込み。**フル機能ECは対象外** |
| 予約システム | 外部予約SaaS埋め込み |
| 記事の更新 | 更新のたびに再書き出し＋再デプロイ（＝運用フローの説明が必須） |

### 3-4. 展開パターン

**パターンA：ノウハウ販売（在庫なし・工数ゼロ）**

- Brain / note / Tips で「WordPressサイトをサーバー代0円にする完全手順」を販売
- 価格帯 2,980〜9,800円
- 画面キャプチャを大量に載せ、つまずきポイント（DNS切替、混在コンテンツ、パーマリンク）を先回りで解説
- 購入者からの個別質問は**受け付けない**か、別料金と明記

**パターンB：半自動代行（中核・ただし件数上限つき）**

- 移行作業そのものを受託。ただし**作業を完全にテンプレ化**して1件2〜4時間に圧縮
- 価格帯 30,000〜80,000円（サイト規模で段階価格：〜50ページ / 〜200ページ / それ以上）
- 納品物：移行済みサイト ＋ 更新手順マニュアル ＋ 旧環境のバックアップ

**パターンC：継続（任意）**

- 記事更新の再デプロイ代行を月額制で提供（月3,000〜10,000円）
- ただし継続案件は再び時間の切り売りになりやすい。
  → **「更新は顧客が自分でできる」状態を標準納品にし、月額は例外**という設計を推奨

### 3-5. 事前に確認すべきチェック項目

- ページ数（見積もりの根拠。ページ数課金にする）
- 会員機能・EC・予約など動的機能の有無 → **あれば対象外 or 別途見積**
- 独自ドメインの管理権限を顧客が持っているか（DNS変更に必須）
- 記事更新の頻度（高頻度なら静的化そのものが不向きな場合がある）
- 既存の広告タグ・解析タグ・外部埋め込みの数

## 4. 運用上の重要注意点（時間の切り売り化を防ぐ）

ここが本メモの本題。**商品自体より、範囲の線引きが利益を決める。**

### 4-1. サポート範囲を明文化する（出品文にそのまま載せる）

```
【本商品に含まれるもの】
・納品時点で動作するツール本体一式
・導入マニュアル（図解付き）／運用マニュアル・FAQ
・納品後 ◯日間の初期不具合対応（こちらの実装ミスに起因するもの）

【含まれないもの】
・納品後の仕様変更・機能追加（別途お見積り）
・Google / Cloudflare / 各種API提供元の仕様変更に伴う改修
・顧客側の環境変更（アカウント変更・権限変更・プラン変更）に起因する不具合
・顧客が独自に加えた改変後の動作保証
・操作方法の個別レクチャー（マニュアル記載範囲を超えるもの）
・APIの従量課金費用、外部サービスの利用料
```

### 4-2. 免責として必ず書く4項目

1. **外部仕様変更の免責**：Google / Cloudflare / OpenAI 等の仕様変更で動作しなくなる可能性があること、その改修は有償であること
2. **API費用の負担者**：APIキーは顧客名義。従量課金は顧客負担
3. **動的機能の制限**（Cloudflare案件）：会員・EC・予約など静的化できない機能があること
4. **データ責任**：移行・自動化にあたりバックアップを取得するが、最終的なデータ責任は顧客側にあること

### 4-3. 「質問ゼロ化」のためのマニュアル設計

サポートが減らない最大の原因は、マニュアルが**文章だけ**なこと。

- **1操作＝1スクリーンショット**。クリックする箇所は赤枠で囲む
- 章立てを「やりたいこと」で切る（機能名で切らない）
  例：×「トリガー設定」 → ○「毎朝9時に自動で動かしたいとき」
- **エラー別FAQ**を必ず用意する。実際に出るエラーメッセージ文をそのまま見出しにする
  → 顧客はエラー文で検索するので、文言一致が効く
- 短い操作動画（画面録画）を1本添える。文章5ページ分の質問が消える
- 問い合わせ導線を「まずFAQを確認 → 該当がなければ連絡」の順に固定する

**運用ルール**：同じ質問が2回来たら、その場でFAQに追記する。
これを続けると商品が回を追うごとに勝手に強くなる。

### 4-4. 見積もり・スコープ管理

- **時間単価で見積もらない。成果物単位・ページ数単位で見積もる**
- 追加要望は必ず「別注文」として起票する（無料で受けない。1回でも受けると基準が崩れる）
- ヒアリングは固定フォーム。通話は有償オプション（または上位プランのみ）
- 「まず相談だけ」への無料対応は、FAQページ / 事前確認シートで代替する

### 4-5. 再現性を高める仕組み

- 自分用の**テンプレートリポジトリ／マスターシート**を持ち、案件ごとに複製して使う
- 顧客ごとの差分は「設定シート1枚」に閉じ込め、コード本体は共通にする
  → 改修が全案件に横展開できる
- 納品済み案件の一覧（顧客・使用バージョン・納品日）を管理し、
  外部仕様変更が起きたときに有償改修の提案先リストとして使う

### 4-6. やらないことリスト

- 顧客のサーバー・アカウントの**長期的な管理責任**を負う契約
- 相場より安い「お試し価格」の常態化（レビュー獲得の初期のみ、期間を区切る）
- 仕様が固まっていない状態での着手
- 動的機能満載のWordPressを無理に静的化すること
- 自分のAPIキーを顧客ツールに埋め込むこと

## 6. ココナラ実践編（販売チャネル別の立ち回り）

> ※手数料率・カテゴリ構成・規約は変更されることがある。**出品前に必ず公式の最新情報を確認**すること。
> 以下は執筆時点の一般的な理解にもとづく整理。

### 6-1. 前提の補正：「出品すれば売れる」わけではない

ココナラは**販売実績数とレビューが検索順位を左右する**構造になっている。
実績0の出品は露出がほぼ無いところからのスタートで、ここを設計せずに出すと1件も売れずに終わる。

つまり勝負どころは商品の出来ではなく、**最初の3〜5件をどう取るか**。

### 6-2. 手数料を織り込んだ価格逆算

販売手数料は **22%（税込）** が目安。売上ではなく**手取り**で価格を決める。

| 販売価格 | 手数料（22%） | 手取り | 実作業2時間なら実質時給 |
|---:|---:|---:|---:|
| 5,000円 | 1,100円 | 3,900円 | 1,950円 |
| 15,000円 | 3,300円 | 11,700円 | 5,850円 |
| 30,000円 | 6,600円 | 23,400円 | 11,700円 |
| 50,000円 | 11,000円 | 39,000円 | 19,500円 |

**判断基準**：手取り ÷ **実拘束時間**（実作業だけでなくDM往復・ヒアリング・納品後対応を含む）が
自分の最低ラインを割る商品は出さない。上表の「実作業2時間」は実際には5〜10時間になりがちで、
そのまま計算すると時給を2〜4倍に見誤る。**実拘束時間の潰し方は7章**。

### 6-3. 実績ゼロを突破する手順

```
Phase 1（実績0〜3件）: 入口商品だけを出す
  ・作業10〜30分で終わる小商品を 1,500〜3,000円 で出品
    例）「既存スプレッドシートに自動集計を1つ追加」
        「フォーム自動返信の設定だけ代行」
  ・目的は利益ではなく レビュー獲得。期間を区切る（1〜2ヶ月）
  ・納品を早く・丁寧に。★5とコメントの質がこの先ずっと効く

Phase 2（実績4〜10件）: 主力商品を並べる
  ・15,000〜50,000円 の導入代行パッケージを追加出品
  ・入口商品は残す（回遊の入口として機能する）

Phase 3（実績10件〜）: 入口商品を絞る / 値上げする
  ・安い商品に時間を取られ始めたら、入口商品を停止 or 値上げ
```

**注意**：Phase 1 の安値を常態化させない。期間か件数で必ず終わりを決めておく。

### 6-4. 出品ページの作り方

**タイトル**（検索されるキーワードを前に置く）

- ✗「業務効率化のお手伝いをします」
- ○「スプレッドシートの集計・転記作業をGASで自動化します」
- ○「WordPressをCloudflareに移行しサーバー代を0円にします」

顧客は「GAS」より「スプレッドシート 自動化」「エクセル 転記 自動」で探す。
**技術名だけでなく、作業名のキーワードを必ず入れる。**

**サービス内容欄の推奨構成**（上から順に）

```
1. こんなお悩みはありませんか？（3〜4行。顧客の作業風景を具体的に）
2. このサービスで解決できること（Before → After を数字で）
3. 納品物（本体＋導入マニュアル＋運用マニュアル/FAQ の3点セットを明記）
4. ご購入からの流れ（ステップ表記。ヒアリングシート方式であることを書く）
5. 料金プラン（成果物単位・ページ数単位の階層表）
6. 【含まれるもの / 含まれないもの】← 4-1 のブロックをそのまま貼る
7. 免責事項 ← 4-2 の4項目
8. よくあるご質問
```

6・7 を書くと売れなくなる気がするが、実際は逆。
**範囲が明確な出品ほど購入されやすく、購入後のトラブルが激減する。**

### 6-5. 見積り・DM対応の運用

- 見積り依頼への**返信速度**が評価指標として効く。テンプレ返信を用意しておく
- 事前ヒアリングは固定フォーム。ここで通話に持ち込まれると利益率が落ちる（4-4参照）
- 対応範囲外の依頼は、断る文面もテンプレ化しておく（曖昧に受けない）
- **外部サービスへの誘導・直接取引は規約違反**。連絡先交換、外部決済、外部サイトへの誘導は
  アカウント停止リスクがある。マニュアルの受け渡しもトークルーム経由か、
  規約で許容される形式に収めること

### 6-6. チャネルの向き・不向き

| 商品 | 向いているチャネル | 理由 |
|---|---|---|
| GAS導入代行（軸①） | **ココナラ** | 「作業を代わりにやってほしい」需要と直結。ただし時間を食う（7章） |
| GASツール本体のみ販売 | ココナラ（コンテンツ販売枠）/ BOOTH | 在庫なしで売れる。ただし単価は上がりにくい |
| Cloudflare移行代行（軸②） | **ココナラ** | サーバー移行カテゴリに需要がある。単価も取れる |
| Cloudflare移行ノウハウ | **Brain / note / Tips** | 手順書コンテンツは情報商材系プラットフォームの方が売れる |

**使い分けの原則**：

## 7. 代行に時間を溶かさないための設計

### 7-1. 時間はどこで溶けているのか

代行1件あたりの時間を分解すると、**実作業はほぼ見積もり通りに終わる**。
溶けているのは実作業の外側。

| 工程 | 見積もり時 | 実際 | 溶ける原因 |
|---|---:|---:|---|
| 見積り依頼のDM往復 | 数えない | 30〜60分 | 個別見積りを受けている |
| ヒアリングと不備の往復 | 15分 | 60〜120分 | 回答が埋まっていない状態で着手する |
| **実作業** | **120分** | **120分** | ← ここは問題ではない |
| 顧客環境の想定外対応 | 0分 | 0〜180分 | 対応環境を限定していない |
| 納品説明・動作確認 | 15分 | 30〜60分 | 口頭・チャットで説明している |
| 納品後の質問対応 | 0分 | 30〜120分 | マニュアルとFAQが薄い |
| **合計** | **2.5h** | **5〜10h** | |

**帰結**：作業をテンプレ化しても、削れるのは既に最短の120分の部分だけ。
効果があるのは**実作業の外側を潰す施策**であって、実装の効率化ではない。

### 7-2. 外側を潰す5つの手当て

| 溶ける場所 | 手当て |
|---|---|
| 見積り往復 | **個別見積りを受けない**。価格を固定表示し、階層から選んでもらう。範囲外は断る（断り文テンプレを常備） |
| ヒアリングの不備 | 「**これが全部揃うまで着手しない**」チェックリストを明示。督促は1回だけ、期限切れはキャンセル |
| 顧客環境の想定外 | **対応環境を限定して出品文に書く**（例：Googleアカウントの管理者権限があること／対象は◯◯以下のページ数／プラグイン◯◯を使用していないこと）。外れたら受けない |
| 納品説明 | 説明を**画面録画5分に固定**。同じ動画を全案件で使い回す。個別の口頭説明をしない |
| 納品後の質問 | FAQ＋対応期間の明記。同じ質問が2回来たらFAQに追記（4-3） |

このうち効果が大きいのは上2つ。**個別見積りと、不備のまま着手すること**が最大の出血点。

### 7-3. 代行の位置づけを変える

代行を「利益の柱」に置くと、売れるほど時間が無くなる。
そうではなく、**ストック商品を作るための調達手段**として期間と件数を区切る。

```
代行から回収するもの（現金以外）
  ・販売実績とレビュー   → 検索露出。これが無いとストック商品も見つからない
  ・生の困りごとの言語化 → 出品文・コンテンツの見出しになる
  ・実際に来た質問       → FAQ、つまりストック商品のマニュアル
  ・繰り返しパターン     → テンプレ化の種
```

**運用ルールの例**

- 代行は **月◯件まで**（上限に達したら出品を一時停止する）
- 同じ内容の代行を **3回やったら、その時点でテンプレ商品化する**
- 顧客ごとの差分は「設定シート1枚」に閉じ込める（4-5）
  → 差分がシート1枚に収まった時点で、それは**コピー納品**に移行できる

### 7-4. 代行からストックへの移行段階

```
段階1  フルカスタム代行      … 1件5〜10時間。ここに留まると時間が溶ける
   ↓   3回やったら
段階2  設定済みコピー納品     … 顧客ごとの差分は設定シートのみ。1件1〜2時間
   ↓   顧客が自分で設定できるマニュアルが書けたら
段階3  テンプレート本体の販売 … 設定は顧客が行う。1件0時間
   ↓   手順が言語化できたら
段階4  ノウハウ販売          … Brain / note。1件0時間
```

段階2に上げるだけで**拘束時間が1/5**になる。まずここを目指す。
段階3・4は在庫ゼロだが、次項の制約がある。

### 7-5. 正直な制約：ストック一本は最初は成立しない

「代行をやめて全部ストックにする」が早すぎると失敗する。理由は集客。

| | 集客 | 1件あたりの時間 |
|---|---|---|
| ココナラの代行 | **プラットフォーム側が持っている**（検索需要がある） | 多い |
| Brain / note のノウハウ | **自分で用意する必要がある**（SNS・ブログ・リスト） | ゼロ |

フォロワーゼロの状態でノウハウを出しても、良い内容でも届かない。
**集客資産が育つまでの間、ココナラの代行がその代わりを務める**——これが代行を残す唯一の理由。

したがって順番はこうなる。

```
ココナラで代行（集客はプラットフォーム任せ）
  → 実績・レビュー・FAQ・テンプレが貯まる
  → 段階2〜3へ移行して1件あたりの時間を圧縮
  → 並行してSNS/ブログで自前の集客を作る
  → 自前集客が立ったらノウハウ販売の比率を上げ、代行の件数上限を下げていく
```

### 7-6. 撤退ラインを先に決めておく

判断を後回しにすると、忙しさで思考が止まって代行を続けてしまう。数値で決めておく。

- [ ] 実拘束時間ベースの時給が◯◯円を下回った案件種別は、出品を停止する
- [ ] 代行の月間拘束時間が◯◯時間を超えたら、新規受付を止める
- [ ] 3回繰り返した代行をテンプレ化していない月が2ヶ月続いたら、代行を減らす
- [ ] 入口商品（Phase 1）の終了条件（期間 or 件数）に達したら、必ず停止か値上げをする
